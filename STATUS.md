## Recent work
- 2026-09-18: **Released v1.8.0** — message templates and an ICS-213 General Message form. Templates carry To/Type/Subject/Body with two placeholder kinds: `{CALL}`-style filled silently at apply time, and `{{prompted}}` collected in a dialog. “Save as…” from the compose window is the intended authoring path. Export/Import as JSON with no-overwrite name collision handling, so a club pack cannot clobber local work. The ICS-213 form reproduces fields 1–8 of the Winlink ICS213 form (Ver 41.12), verified against the form image in KN4LQN's Winlink Wednesday guide; it renders to readable text at REVIEW and refuses an incomplete form. Explored integrating N3MEL's 15-form TPRFN suite and Jason decided against it — scope stays at the three native forms.
- 2026-09-18: Corrected a wrong claim I had baked into a code comment: BPQ *can* carry attachments (B2 format, via RMS/SMTP/ISP interfaces). The reasons not to emit ICS-213 XML are different — binary attachments are not accessible to BBS readers, and whether EMSave accepts a file part is undetermined because BPQ's compose page sits behind the session key. Noted in the code for whoever picks it up. Also found that BPQ WebMail has built-in Winlink HTML template support (`Standard_Templates` / `Local_Templates` under the BPQ32 directory) — neither directory exists on Jason's node, so it has never been used.
- 2026-09-18: Ran down a "serving the old version" report and a separate "works in Firefox, not Chrome" report — both trace to the same **BPQ web-server bug**: it caches a file's `Last-Modified` the first time it serves that path and never re-stats, sends no `ETag`/`Cache-Control`, and ignores `If-Modified-Since` (always 200). Evidence: the deployed file reported 27 Aug while its mtime was 17 Sep; the TEST copy reported that morning; a brand-new filename reported correctly. Browsers therefore cache heuristically (~10% of the implied age ≈ 2 days here) and Chrome/Firefox differ in how they apply it. No app bug. Documented as Report 2 in `UPSTREAM-REPORT-G8BPQ.md`, added a hard-reload note to both install paths in the README, and verified `?v=` cache-busting does not disturb host/port auto-detection. Also deployed the `fonts/` directory to the node — all six woff2 files had been 404ing since the app was first installed, so every browser was silently falling back to a substitute font (another candidate for cross-browser appearance differences). Removed `bpq-alt-webmail-TEST.html` from the HTML directory.
- 2026-09-17: Late addition to v1.7.0 before announcing it: removed **T – NTS Traffic** from the compose Type dropdown and relabelled the radiogram entry **T = NTS (Radiogram Form)**, so NTS traffic is composed through the form rather than freehand. Not a pure label change — `rgReview()` reached wire type T by *selecting* it in that dropdown, so deleting the option would have trapped the radiogram in an endless REVIEW loop. Replaced with a `forcedType` variable carrying the wire type alongside the dropdown; the documented `#compose?type=T` dashboard link uses the same path. 19 new assertions (typetest.js) drive every compose type against a stub node and assert what each actually POSTs. Release re-cut in place (tag moved, GitHub Release updated, asset replaced) — it was minutes old with zero downloads.
- 2026-09-17: **Released v1.7.0.** Version bumped in the three places, CHANGELOG entry dated, README rewritten (Address Book section, bulletin subscribe/unsubscribe, right-click menu, Save Sender), committed and pushed to `main`, tagged `v1.7.0`, GitHub Release published. ## Decisions & blockers
- **BPQ's web server caches `Last-Modified` per path and never refreshes it.** Any file update in the HTML directory therefore needs a browser hard-reload (or a `?v=` query) to be seen; without one the browser may sit on its copy for a day or more. Chrome and Firefox differ here, so this masquerades as a cross-browser bug. Check `curl` against the browser before believing any "works in X but not Y" report.
- **`gh` is NOT installed on this machine** (confirmed 2026-09-17) — the CLAUDE.md release checklist's step 7 assumes it. Git push/tag work fine (a PAT for `jayflanzbaum-svg` is in Credential Manager), so GitHub Releases are created here by calling the REST API with that PAT instead of `gh release create`.
- **The send iframe must stay sandboxed.** BPQ's reply pages carry their own `alert()` calls; without `sandbox="allow-forms allow-same-origin"` those become one modal per recipient on any multi-recipient send. Keep `allow-same-origin` (the reply is parsed by `bpqReplyNotice()`), and never add `allow-scripts` or `allow-modals`.
- Bulletin **unsubscribe** is deliberately a *local view filter* (`bpq_bull_unsub` in localStorage), not a BBS-side change. **Reject** already exists for the server-side action of telling the node to stop accepting that traffic; unsubscribe is the softer "I don't want to look at this" and is reversible with no node round-trip. Unsubscribed TOs are kept visible (dimmed, ⊘) at the bottom of the Bulletins tree rather than disappearing, so there is always a discoverable way back.
- Contact **groups reference callsigns**, they do not embed contact records — so one edit propagates, and a contact can be in several groups. This is the Gmail-label model; Outlook's copy-into-the-list model would need a modal member picker that does not fit the pane.
- **QRZ has no settings section by design.** It is one-time setup that was taking up the top of the address book, so the lookup link now opens the login prompt on demand and resumes the lookup afterwards. If a QRZ control is ever needed elsewhere, reuse `openQrzLogin(whyHtml, then)` rather than adding a settings block back.
- **Group membership is picked by typing, not by a checkbox list** (2026-09-17). A checkbox well does not survive a few dozen groups, and it gave no way to create one in place. The picker (`gpInit`/`gpOpen`/`gpPick` in the GROUP PICKER block) is generic — instantiate it with an id, a Set and an onChange; reuse it rather than writing a third group UI. Note its Set is bound at `gpInit()` time, so re-init whenever the owning dialog reopens and reassigns that Set.
- **Creating a group from a picker writes it immediately**, so cancelling the card or the import still leaves the new (empty) group behind. Deliberate — it shows up in the rail at once and matches how Gmail labels behave — but it means an abandoned import can leave an empty group to tidy up.
- **A contact is edited in a dialog, never in a fixed pane.** A permanent add-contact form cost a third of the window for something done occasionally, and — more to the point — a "saved silently with a toast" quick-add read as a broken button. Anything that files a station should show the card. Reuse `openContactCard(call)` / `openContactCard(null, seedCall)` rather than adding another inline form.
- **Import never overwrites an existing contact's details** — it only fills blank fields. A club roster re-imported after hand-editing a name must not wipe that edit, and there is no undo.
- A contact record grew to `{call,name,street,city,state,zip,phone,email,web,notes,useCount,lastUsed}` (2026-09-17). Everything past `state` is optional and older records have it blank/undefined — read with `|| ''`, never assume presence.
- The contact list renders at most `AB_RENDER_CAP` (400) rows. It is plain innerHTML, so an unbounded book would rebuild a huge string on every keystroke of the filter; raise the cap only alongside real virtualisation.
- Intentionally a single self-contained HTML file: no build step, no toolchain, no runtime dependencies (fonts are local woff2 files). Editing means editing the one file and testing against a real BPQ node.
- Jason's actual node HTTPPORT is **8010**, not 8080 — 8080 is only the app's first-run setup-screen placeholder default. Confirmed 2026-08-25 via curl (8080 connection-refused, 8010 serves the app). Don't assume 8080 when reasoning about his live setup.
- BPQ32's built-in web server sends no CORS headers at all (confirmed 2026-08-25 via curl — no `Access-Control-Allow-Origin` even with `Origin: null`). The app must be loaded from BPQ's own server (same-origin, e.g. `http://127.0.0.1:8010/bpq-alt-webmail.html`) — opening the local file directly (`file://`, e.g. double-clicking it in Explorer) breaks every fetch to the node and also lands in a different, mostly-empty localStorage bucket (Chromium/Edge share one storage bucket across all `file://` pages, unrelated to the real one used at the `http://127.0.0.1:8010` origin).
- This dev environment can reach Jason's live BPQ node directly at `127.0.0.1:8010` (confirmed 2026-08-11 via curl) — raw endpoint checks no longer need to wait for Jason.
- Killed messages are hidden client-side and remembered in localStorage because BPQ marks-but-doesn't-purge; body cache capped at 30 (FIFO), killed list at 500.
- Single-branch workflow since 2026-08-05: all work happens on `main`; releases are marked by tags + GitHub Releases (latest: `v1.6.8`, 2026-09-10). The old `experimental/jay-dev` dev branch was deleted once it had fully converged with `main`.
- BPQ grants sysop status purely by connecting IP and **ignores `X-Forwarded-For`** (verified 2026-08-28: `curl -H "X-Forwarded-For: 8.8.8.8"` to `/Node/EditCfg.html` still returned the full 7,529-byte config). So any reverse proxy or tunnel daemon running *on the BPQ machine* connects from 127.0.0.1 and hands the whole internet automatic sysop — Edit Config, web Terminal, BBS logs. `EditCfg` serves `BPQ32.cfg` verbatim, which holds the telnet `USER=` password and `CMSPASS=` in cleartext. Any tunnel/proxy setup must carry its own authentication in front.
- BPQ32's web server has no TLS of any kind (no `HTTPSPORT`/cert options — confirmed in G8BPQ's `BPQWebServer.html` docs). Any HTTPS has to come from something in front of it.
