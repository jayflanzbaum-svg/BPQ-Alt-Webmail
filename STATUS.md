- 2026-09-22: **Address-book sync between your own PCs, through the BBS** — no manual export/import (N3MEL's request). Each PC keeps one P-type message to your own callsign, subject `[ABSYNC] <device>`, holding the book base64-encoded at 76 columns between `---BEGIN BPQ-ALT-AB v1---` markers; `parseList(html, keepSync)` hides these carriers from the whole UI. Merge is per record, newest `updated` wins, with tombstones. Pull rides the 5-minute poll (90s throttle) and the address-book open; push is debounced 45s and replaces this device's previous carrier. One footer control, off by default. 19-assertion two-device simulation passes; it caught a real bug (tombstone test used `>=`, so unstamped legacy records were all dropped — the first sync of two existing books would have moved nothing).
- 2026-09-22: **★ Favorite a bulletin topic** (N3MEL's request) — the positive counterpart to unsubscribe. A favourited TO pins to the top of the Bulletins tree under a ★ Favorites roll-up, and `evalRules()` reports its messages as starred, so the existing ★ filter does the work rather than a second filtering concept. Favourite and unsubscribe clear each other. Stored in `bpq_bull_fav`. 19 assertions across two harnesses.
- 2026-09-22: **Attachment round trip confirmed** (test msg 4082, still in the mailbox — kill it). `EMSave` accepts a `myFile[]` part; the file comes back inside the same textarea `parseBody()` already reads, after an `Attachment <name>` line, byte-for-byte. `DL?<key>&<num>` lists attachments (warns >100K can't be downloaded); `GetDownLoad` is unusable from a scripted client and isn't needed.

## Decisions & blockers
- **Dev scripts live in `.claude/dev/`** (gitignored, so they never reach the release): `sync-size-probe.ps1` and `attach-probe.ps1` are live-node probes Jason must run himself (this session can't send mail); `synctest.py` regenerates the two-device sync simulation and `favtest.js` / `startest.js` are the bulletin-favourites harnesses. They work by extracting the real functions out of the single HTML file, so they follow along with edits rather than duplicating logic.
- **The mail store is the only writable shared storage a browser can reach on a BPQ node** (probed 2026-09-20/22). That is why address-book sync is mail, not a file. Don't revisit the HTML-directory idea for anything that needs writing.
- **Sync merges per record, not per book.** Whole-book last-write-wins would discard a contact added on the other PC. Tombstones (`bpq_ab_ctomb`/`bpq_ab_gtomb`, pruned at 90 days) exist because a partner still holding a deleted contact would otherwise put it back. Unstamped legacy records merge field-by-field, filling blanks — and note "no tombstone" and "unstamped" are both `0`, so tombstone tests must check the stamp is truthy before comparing.
- **`saveContacts`/`saveGroups` are the only writers of `bpq_contacts`/`bpq_groups`**, which is why stamping, tombstoning and push scheduling all hang off `abStamp()` there. Keep it that way — a direct `LS.setJ` write would silently skip all three.
- **`useCount`/`lastUsed` are per-machine and never synced**, and are excluded from the change comparison too — otherwise every send would stamp a contact and trigger a push.
- **Sync payloads are base64 at 76 columns between markers**, not raw JSON: a BBS path is not guaranteed 8-bit clean or free of line wrapping, and reassembly strips all whitespace so a wrap costs nothing.
- **BPQ's web server caches `Last-Modified` per path and never refreshes it.** Any file update in the HTML directory needs a hard-reload or a `?v=` query. Chrome and Firefox differ here, so it masquerades as a cross-browser bug — check `curl` against the browser before believing any "works in X but not Y" report.
- **`gh` is NOT installed on this machine** (confirmed 2026-09-17); the CLAUDE.md release checklist assumes it. Git push/tag work (PAT in Credential Manager), so create GitHub Releases here via the REST API instead.
- **This session cannot send mail** — the auto-mode classifier blocks a POST to `EMSave` as a real-world transaction. Anything needing a live send has to be handed to Jason as a `! powershell -File …` one-liner.
- **The send iframe must stay sandboxed.** BPQ's reply pages carry their own `alert()`; without `sandbox="allow-forms allow-same-origin"` a multi-recipient send is one modal per recipient. Keep `allow-same-origin`, never add `allow-scripts` or `allow-modals`.
- Bulletin **unsubscribe** is a local view filter (`bpq_bull_unsub`), not a BBS-side change — **Reject** already does the server-side thing. **Favorite** (`bpq_bull_fav`) is its positive counterpart and reuses the existing star filter rather than adding a second filtering concept; the two clear each other so a topic is never both.
- Contact **groups reference callsigns**, they do not embed contact records (the Gmail-label model). **Group membership is picked by typing** via the generic picker (`gpInit`/`gpOpen`/`gpPick`) — reuse it rather than writing a third group UI, and re-init it whenever the owning dialog reassigns its Set. **Creating a group from a picker writes it immediately**, so an abandoned import can leave an empty group behind (deliberate).
- **A contact is edited in a dialog, never in a fixed pane** — reuse `openContactCard(call)` / `openContactCard(null, seedCall)`. **Import never overwrites**, it only fills blank fields. The contact list renders at most `AB_RENDER_CAP` (400) rows; raise it only alongside real virtualisation.
- **QRZ has no settings section by design** — the lookup link opens the login prompt on demand via `openQrzLogin(whyHtml, then)`.
- A contact record is `{call,name,street,city,state,zip,phone,email,web,notes,useCount,lastUsed,updated}`; everything past `state` is optional and older records have it blank — read with `|| ''`.
- Intentionally a single self-contained HTML file: no build step, no toolchain, no runtime dependencies (fonts are local woff2 files). Testing means editing the one file and running it against a real BPQ node.
- Jason's node HTTPPORT is **8010**, not 8080 (8080 is only the first-run placeholder). This dev environment can reach the live node directly at `127.0.0.1:8010`.
- BPQ32's web server sends **no CORS headers**, so the app must be loaded from BPQ's own server — opening the file over `file://` breaks every fetch and lands in a different localStorage bucket.
- BPQ grants sysop status by connecting IP and **ignores `X-Forwarded-For`**, and `EditCfg` serves `BPQ32.cfg` verbatim (telnet `USER=` password and `CMSPASS=` in clear). Any proxy/tunnel on the BPQ machine hands the whole internet sysop unless it carries its own authentication. BPQ has no TLS of any kind.
- Killed messages are hidden client-side and remembered in localStorage because BPQ marks-but-doesn't-purge; body cache capped at 30 (FIFO), killed list at 500.
- Single-branch workflow since 2026-08-05: all work on `main`; releases are marked by tags + GitHub Releases (latest `v1.8.0`, 2026-09-18).
